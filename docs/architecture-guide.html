01 / MENTAL MODEL

Not a chatbot.
A controlled runtime.

Vibe is a local orchestration system around an LLM. The model proposes text and typed tool calls; Vibe owns permissions, execution, state, persistence, and presentation.

The key idea: the model never directly edits a file or runs a command. It emits a structured request. Vibe validates it, applies policy, may ask you, executes it, records the result, and sends that result back to the model.

local-firstasynctyped eventspermissioned toolsstreamingmulti-surfaceresumableextensible

Model

Chooses the next action

Receives the system prompt, conversation, tool schemas, and project context. It streams prose, reasoning, and function calls.

Harness

Owns execution

The app server owns sessions, turns, callbacks, resources, queueing, projections, and cleanup across every client.

Client

Renders and participates

The terminal or IDE displays public events, gathers approvals and answers, and can provide explicitly advertised local I/O.

03 / STARTUP

From vibe
to a live session.

Startup is deliberately lazy. Heavy UI, MCP, connector, and runtime work is delayed until the selected path needs it.

Tiny launcher selects a terminal

VIBE_CLI=rust execs the Rust binary; otherwise the Python entrypoint is imported. Setup and update checks stay Python-only.

vibe/cli/launcher.py

Bootstrap local state

Vibe secures its home directory, loads environment credentials, resolves the working directory or worktree, initializes logging, and prepares trusted project sources.

vibe/cli/entrypoint.py · vibe/core/paths · vibe/setup

Choose a delivery path

Interactive mode starts Textual or the opt-in Rust TUI; --prompt starts the headless runner; vibe-acp serves editors. Each becomes an app-server client.

vibe/cli/cli.py · vibe/cli/programmatic.py · vibe/acp/entrypoint.py

Handshake over JSON-RPC

The client sends initialize, advertises callback and client-tool capabilities, then sends initialized. Ordinary requests are rejected before this handshake.

vibe/app_server/host.py · client.py · server.py · protocol.py

Open, resume, or continue

The host starts a blank session, loads one by ID, or resolves the latest eligible session. Only now does the selected backend create or restore runtime state.

vibe/app_server/session.py · _session_backend_port.py · _runtime.py

Build a canonical snapshot

The client receives public session history, active callbacks, turn state, queue state, resources, and an event watermark, then subscribes to ordered updates.

vibe/app_server/models.py · events.py · client_state.py
04 / THE LOOP

What happens in
one agent turn.

A “turn” can contain many model steps. The loop continues while the latest model response asks for tools, then stops when it produces a final assistant response.

01Accept inputNormalize text, images, mentions, and resources.
02Prepare contextInject skills/files and run limits or auto-compaction.
03Call modelStream reasoning, text, usage, and typed tool calls.
04Gate toolsValidate arguments, hooks, policy, and user approval.
05ExecuteRun independent calls concurrently and stream output.
06Commit resultAppend tool messages, save state, and continue or finish.
↖ tool results become model context; repeat from step 02

Output arrives incrementally

AgentLoop.act() is an async generator. Streaming model chunks become ReasoningEvent, AssistantEvent, and early ToolCallEvent values. The app server projects those into stable public history entries while clients repaint.

A batch of calls can run in parallel

When one assistant message contains multiple tool calls, Vibe creates one task per call and funnels events through a queue. Cancellation propagates to unfinished tasks. A sentinel closes the batch only after all tasks settle.

Policy runs before every model step

Turn, price, and token limits can stop the loop. Auto-compaction can replace old context with a summary. Context warnings inject guidance, and plan mode adds read-only reminders. A context-overflow failure can trigger one reactive compaction and retry.

Typed events decouple engine and UI

Core emits user, assistant, reasoning, tool, approval, compaction, title, hook, and lifecycle events. The app server turns them into public message, reasoning, effect, callback, checkpoint, and notice entries with stable IDs.

open_user_turn()
while true:
    decision = middleware.before_turn(context)
    if decision.stop: break
    if decision.compact: compact_context()

    response = stream_model(messages, available_tool_schemas)
    emit(response.text, response.reasoning, response.tool_calls)

    if response.tool_calls:
        results = await run_tools_concurrently(response.tool_calls)
        append(results)
        save_session()
        continue

    run_post_agent_hooks()
    save_session()
    break
05 / TOOLS & SAFETY

Capabilities with
guardrails.

Tools are Pydantic-typed ports into side effects. Every call has validated arguments, a permission decision, streamed progress, and a typed final result or error.

1 · Discover

Build the catalogue

Load built-ins, configured paths, project and user tools, MCP tools, and connector tools. Apply per-source and global enable/disable filters.

2 · Validate

Parse model arguments

The model’s JSON is validated against the tool’s Pydantic argument type before execution. Invalid calls become model-visible tool failures.

3 · Pre-hook

Inspect or rewrite

Matching pre_tool hooks may deny a call or fully replace its input. Rewritten arguments are validated again.

4 · Permission

Allow, ask, or deny

Config, allowlists, denylists, sensitive patterns, workspace boundaries, session grants, or smart classification determine the verdict.

5 · Execute

Run through one contract

Tool output may stream. File-changing tools can capture a before-state checkpoint. Some I/O can be delegated to an authenticated client capability.

6 · Post-hook

Audit or transform

post_tool hooks see status, duration, output, and errors. They may replace model-visible output or append context.

Safety is layered, not a single prompt. Workspace trust controls project-provided configuration. Tool policy controls side effects. Shell analysis inspects nested commands and outside-directory paths. Public projections redact secrets. Auto-approve intentionally bypasses prompts and should be used cautiously.

06 / CONTEXT & MEMORY

What the model sees
is carefully assembled.

The visible transcript, private durable session, and current model context are related but intentionally different representations.

System context

Identity and operating rules

Built-in or custom prompt, OS and shell guidance, available tools and skills, project path, Git metadata, additional roots, and trusted AGENTS.md instructions.

Conversation

Messages and tool outcomes

User input, assistant responses, reasoning metadata, function calls, and tool responses are maintained as typed LLMMessage values.

Compaction

A boundary, not a new session

Vibe summarizes older work, preserves recent user messages, appends a marked compaction checkpoint, and sends only that boundary plus newer messages on later calls.

Durability model

Ordinary message writes are append-friendly; metadata writes are atomic. A stored session includes conversation state, metadata, statistics, tool availability, and resumability data. It does not make in-flight work crash-recoverable.

Rewind model

A rewind can fork a new session and preserve the source, or explicitly truncate in place. Optional file restoration uses checkpoints captured around edits and remains separate from transcript persistence mode.

Public state is lossy by design. Clients receive safe, renderable PublicSessionState and page history with opaque cursors. Only the server reads private session files or reconstructs the engine.

07 / CONFIGURATION

Eight layers.
One effective snapshot.

VibeConfigSchema is canonical. Each field has validation and merge behavior. Higher layers override lower ones, while structured fields may replace, union, concatenate, or merge.

01Schema defaultsAlways present
02GrowthBook experimentsServer-supplied rollout assignments
03User TOML~/.vibe/config.toml
04Trusted project TOMLNearest discovered .vibe/config.toml
05EnvironmentVIBE_* values
06Session overridesCLI flags and ephemeral runtime choices
07Agent profileTools, model, prompt, and policy for the active mode
08Admin policyOrganization-enforced values; highest priority

Attached clients never edit TOML directly. They call typed config/read, config/write, or config/reload resources. The app server validates the prospective merged config, writes atomically where applicable, rebuilds derived state, and returns the canonical runtime snapshot.

09 / SURFACES

Same runtime,
different experience.

Every delivery surface uses the public app-server facade. That keeps session and tool behavior aligned while allowing each client to own presentation.

Python interactive client

Textual owns widgets, keyboard behavior, transcript rendering, autocomplete, local clipboard integration, voice UX, and screens. It consumes AppServerSession; production code under vibe/cli/textual_ui is explicitly kept free of core imports.

Thin Ratatui client

The optional VIBE_CLI=rust path launches vibe-rs. It talks newline-delimited JSON-RPC over stdio to the Python app server and follows a unidirectional Action → reduce(AppStore) → Effects architecture. It does not duplicate the agent runtime.

Editor and IDE adapter

vibe-acp translates Agent Client Protocol sessions, prompts, modes, tool updates, elicitation, and client filesystem or terminal calls to the same app-server methods and events used by the TUIs.

Programmatic CLI

vibe --prompt starts the same local harness, consumes public events, denies unresolved callbacks, and outputs final text, a JSON history array, or newline-delimited streaming JSON. Turn, cost, token, and tool filters are session options.

10 / SOURCE MAP

Where to look
in the repository.

The fastest way to read Vibe is by following ownership boundaries, not by opening files alphabetically.

vibe/core/agent_loop/The legacy Python engine: opens turns, calls the model, executes tools, compacts context, emits typed events.
vibe/app_server/The harness boundary: JSON-RPC, session backends, queues, public projections, resources, callbacks, lifecycle.
vibe/core/tools/BaseTool, discovery, filtering, permissions, built-ins, MCP and connector adapters, terminal runtime.
vibe/core/config/Pydantic schema, eight-layer orchestrator, migrations, models, environment and persistent sources.
vibe/core/session/JSONL messages, atomic metadata, loading, indexing, leases, titles, and cross-harness interop.
vibe/core/checkpoints/File snapshots that support review and optional rewind restoration.
vibe/core/skills/Agent Skills parsing, discovery, invocation policy, built-ins, and registry materialization.
vibe/core/hooks/Typed pre-tool, post-tool, and post-agent subprocess pipelines.
vibe/cli/textual_ui/Python terminal presentation and interaction, deliberately downstream of the app-server API.
vibe/cli-rust/Rust terminal client, reducer, effects, protocol adapter, UI, commands, selection, and voice.
vibe/acp/ACP server, content and session translation, auth, client tools, commands, and updates.
harness/Bundled Unified Harness native/runtime source, selected behind the same app-server backend port.
tests/Mirrors source ownership; focused app-server, core, ACP, TUI, protocol, safety, and boundary coverage.
11 / LEARNING PATH

Read it in
this order.

This sequence builds a working model before exposing implementation detail.

Run the product

Try interactive mode, a tool call that needs approval, /compact, /resume, and vibe --prompt "…" --output streaming.

Read the architecture decisions

Start with ADRs 0001–0007 and 0009. They explain ownership rules that raw call graphs cannot.

Trace a headless request

Follow cli.py → programmatic.py → LocalHarness → AppServerHost → AppServerSession.act(). This avoids UI noise.

Trace the engine loop

Read AgentLoop.act(), _conversation_loop(), streaming response handling, and _run_tools_concurrently().

Study one tool end to end

Pick read_file or edit: schema, permission resolution, hook pipeline, execution, event projection, and rendering.

Then choose a specialty

Configuration, persistence, skills, MCP, subagents, Textual, Rust, ACP, voice, worktrees, or the Unified Harness backend.

Important migration detail: the app server can select a legacy Python AgentLoop backend or the bundled Unified Harness backend through a common session-backend port. The Unified Harness is the current default; --legacy-harness is the escape hatch. Treat the app-server contract as stable architecture; backend internals are implementation choices.
